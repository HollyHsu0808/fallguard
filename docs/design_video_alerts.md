# FallGuard × n8n — workflow build with video alerts (design)

Date: 2026-09-13. Source: `n8n_build_guide.md` (v1 hackathon guide) + `fallguard_v9` app.

## Goal
Build the full "FallGuard Flow 2" n8n workflow from the guide, with one change:
the Telegram alerts must show **what happened at the fall** as a short video
clip (the product's differentiator), not only text. Photo is the fallback when
no clip is available; plain text is the fallback when neither is available.

## Constraints found
- n8n Cloud trial exposes no public API and no `n8n API` settings entry, so the
  workflow is delivered as an importable JSON file, not created over the API.
- The app payload today carries only two base64 JPEG snapshots; there is no
  video. Video therefore requires an app-side change.
- No system ffmpeg on the dev laptop; `opencv-python` wheels have no H.264
  encoder. Telegram mobile clients only inline-play H.264/AAC mp4, so the clip
  must be encoded with libx264 → use the `imageio-ffmpeg` bundled binary.

## Part A — app: fall clip in the payload
Files: `fall_episode.py`, `app_v9.py`, `test_fall_episode.py`.

- `ClipBuffer` (new, in `fall_episode.py`): ring buffer of the last
  `pre_sec` (default 5 s) processed display frames as JPEG bytes with their
  video timestamps. `push(video_time, frame_bgr)`; `snapshot()` returns the
  frames currently held.
- `encode_clip(frames, fps) -> base64 mp4 or None`: pipes the JPEGs into
  ffmpeg (`image2pipe`, `libx264`, `yuv420p`, `+faststart`, crf 28, max 640 px
  wide). Falls back to `cv2.VideoWriter` (`avc1`, then `mp4v`) when
  `imageio_ffmpeg` is missing; returns None when everything fails.
- `FallEpisode` gains `clip_b64`, `clip_meta` (`duration_sec`, `fps`,
  `pre_fall_sec`, `post_fall_sec`, `codec`).
- `build_payload(..., include_clip=False)` adds
  `payload["clip"] = {"mp4_base64", "duration_sec", "fps", "pre_fall_sec",
  "post_fall_sec", "codec"}` when `include_clip` and a clip exists. Snapshots
  unchanged.
- `app_v9.py`: sidebar checkbox "Include fall clip (mp4) in payload" (default
  on). Every processed frame is pushed to the ClipBuffer after banners are
  drawn. On fall detection the pre-fall frames are captured; post-fall frames
  keep accumulating until the analyser finishes (~2.5 s) → the clip is encoded
  once and stored on the episode, so `fall_analysed`, `escalation` and
  `episode_closed` all carry the same fall clip. The "Send test payload"
  button builds a synthetic 3 s clip so the n8n video path can be tested
  without a video.
- Tests: `ClipBuffer` retention window, `encode_clip` round-trips to a
  decodable mp4 (skipped with a message when no encoder), payload contains
  `clip` only when asked and available.

## Part B — n8n workflow JSON
Generated by `fallguard_n8n/build_workflow.py` → `fallguard_n8n/FallGuard Flow 2.json`.
All node names follow Appendix B of the guide, except the Telegram alert
section which becomes a shared media chain:

```
Build alert ─┐
             ├─> IF has clip ──true──> Clip to file ──> Telegram video
Build escalation ┘        └──false──> IF has snapshot ──true──> Snapshot to file ──> Telegram photo
                                                     └──false──> Telegram text
```
`Build alert` / `Build escalation` output `{chat_id, text, clip_b64, photo_b64}`.
Video/photo captions carry the alert text (HTML parse mode, ≤1024 chars).
Every other Telegram node (GP reminder, Obs reminder 1/2, Follow-up) stays text.

Everything else (Event log, Switch, IF false alarm, Profile lookups, Assemble,
Grading, Report + Anthropic chat model, Report email, Caregiver form, Switch
decision, three branches, Outcome form, Stage 4) is built exactly as the guide
describes, with the Code node scripts and prompts embedded verbatim.

Credentials are referenced by type only; n8n auto-selects the sole credential
of each type after import. The Google Sheets document must be picked once per
node (documented in the README).
